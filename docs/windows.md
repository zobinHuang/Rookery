# Windows and the stage

How MuxShots sees windows, takes them over, and lays them out on its stages.

## Seeing windows

- **Identity**: a window is its `CGWindowID` (`WindowId`). Accessibility elements carry no stable id, so the read-only private `_AXUIElementGetWindow` maps an element to its window id (`PrivateAccessibilityApi.swift`).
- **Window server**: `CGWindowListCopyWindowInfo` sees every window on every Space but gives no handle to move it. The private read-only `CGSWindowIsOrderedIn` tells windows really shown from those an app closed but keeps alive (Electron does).
- **Accessibility**: `kAXWindowsAttribute` lists only the current Space's windows. Windows on other Spaces are found by brute force through `_AXUIElementCreateWithRemoteToken`, in slices of ids up to a limit; only elements that are windows count, and an element once found stays valid across Spaces.
- **Tracking** (`WindowTracker`, `ApplicationWindowTracker`): an `AXObserver` per application on a run loop thread of its own, observing managed windows only. Window-level events are coalesced for 250 ms and read only the changed window; app-level structure changes and a 10-second fallback reconciliation read a full snapshot. Accessibility calls are synchronous IPC and can hang on a stuck app, so the main thread never makes them. A managed window that closed before it was ever observed is reported removed.

Nothing writes window-server state through private APIs; Spaces are never moved or switched.

## Taking windows over

- A window is managed only when the user drags it onto a stage (or `muxctl manage`); other apps' windows are never touched.
- A dropped window is adopted only once it outlives the drop by 0.15 s: dragging a tab out of Chrome makes a window that Chrome merges back and closes at once.
- **Hiding** a window parks it off screen in a corner (`ScreenGeometry.offscreenFrame`) rather than minimizing it, which animates and is slow. Its `restoreFrame` and `homeFrame` are kept in `workspace.json`.
- **Parked windows keep drawing.** macOS does not let a window leave the screen entirely, and a window with a sliver on screen counts as visible however little shows, so its application goes on rendering it at full rate (an opaque window over the sliver does not change that). Half a second after layout settles, every application whose windows shown on any Space are all parked is hidden whole (`NSRunningApplication.hide`), which does stop it; it is unhidden before any of its windows is shown again. An application with another window on screen, or the active one, is left as it is; a window of its own off every display, such as the link bubble Chrome leaves beside a parked window, does not count. So is a browser playing a video in the sidebar: a hidden browser stops drawing the page, and the video freezes. Each extension connection carries its browser's process id, the parent of the native messaging host, and a browser that starts playing one while hidden is unhidden. A hidden application's windows still exist in the window server's list, so the tracker does not take them for closed.
- **Windows their application orders out**: WeChat orders its window out a second or two after it is parked, and Accessibility stops listing it. Showing such a window asks its application to reopen, as a click on its Dock icon does, and moves the window once it is listed again; a window that still cannot be moved stays marked hidden, so the next switch tries again. Putting every window back at launch and quit reopens them the same way, and a saved window that is ordered out still counts as alive: `CGWindowListCopyWindowInfo` with `.optionIncludingWindow` omits such a window, so liveness is read from the full list.
- **Crash safety**: on launch and on quit, every hidden or staged window is put back where it was, so no window is ever left off screen.

## Stages

- A stage (`StageController`) is a borderless, non-activating, resizable panel at normal level. It is kept just beneath its front window (`order(.below, relativeTo:)`), so the managed window looks hosted inside it while staying a real window of its app. AppKit orders a pressed window to the front, so a press on the stage puts it straight back beneath that window (`StagePanel.sendEvent`) rather than covering it until the window is brought forward.
- **Several stages**: each owns its own groups. A stage moves with its front window while that is dragged (coalesced relayout), and dragging the stage moves its windows.
- **Displays**: `StagePanel` overrides `constrainFrameRect` so AppKit does not pin it to one display, and settles on the display under the cursor after a move.
- **Display changes**: a display that comes, goes or wakes (a lid closed and opened, a monitor plugged in) makes macOS move windows by itself, parked ones back on screen included, and can move the origin of the window server's coordinates. One and four seconds after such a change, each stage is fitted back onto the display it is mostly on and its front window refitted, and every hidden window found on screen is parked again.
- Frames for layout come from Accessibility, not the window server: during Space animations the window server reports skewed frames.
- **Switching**: ⌃⌥1–9 and the group switcher (⌥⇥) switch groups; ⌘⇥ is taken over by an event tap (`KeyInterceptor`) only while a stage is in front, offering windows most recently used first across groups. The switcher wraps its cards into rows that fit the stage it opens over.
- **Focus that follows a hidden window**: a hidden window that takes focus and keeps it for 150 ms is taken as chosen, and its group and tab are switched to, as when a notification brings it forward. Right after a switch, though, the application of the window brought forward can settle its focus on one of its own parked windows (Chrome does): for 1.5 s such a focus is taken back to the window brought forward instead, or a click on a tab would land on another.
- **Show before hiding**: a stage switch moves the new front window into the content area and raises it before it moves the old one off screen, so the content area is never left empty for the frames in between, which flashed.

## Sidebar

The sidebar is SwiftUI in the stage's hosting view: the Groups/Mixer/Notes switch, then the groups, the mixer or the quick notes, then sidebar videos, code agent limits, the world clock, and the toolbar. Colors are tokens in `StageColors` that follow the light and dark themes (dark is near black); theme changes crossfade through a snapshot of each stage.

Every assignment to an `@Observable` property redraws the views reading it, equal value or not, so `StageController.refresh` assigns only what changed, and a layout change tells the views once when it ends rather than once for each window it moves. Window names live in `StageModel.mapWindowNames`, read only by the texts showing them (`WindowNameText`, `GroupSubtitleText`): pages such as Gmail retitle their window every few seconds, and that must not rebuild the stage.

Tabs that do not fit scroll sideways, faded at an edge with more beyond it, and the bar scrolls to a tab when it is selected. The bar keeps only whether tabs lie past either edge, not the scroll offset, so scrolling does not rebuild the stage; the tabs' backgrounds are keyed by position, since a second view with a window's id would be where scrolling to that window lands.

**No SwiftUI animation runs for long on the stage.** While any SwiftUI animation runs, every frame redraws the whole stage on the CPU, its text and icons included: the tab bar's sliding selection cost a third of a second per switch and the refresh symbol a full core while it turned. Motion that lasts is Core Animation on a layer of its own instead, which the render server runs while the stage draws nothing: the selected tab's background (`TabHighlight`), the refresh symbol (`SpinningSymbol`), the clock's colons.

Quick notes (`QuickNotes`, `NotesView`) are shared by every stage and saved to `notes.json` beside the workspace whenever one changes. A click edits a note in place: the stage panel takes keyboard input as it does for renaming, the editor is a `TextEditor` that grows with the text, return adds a line, escape puts the text back, and a note left blank is deleted. A click anywhere else saves: on the sidebar's empty space (which also finishes a name being edited), on another note or mode, or outside the stage, which takes keyboard input from the panel; the editor watches `NSWindow.didResignKeyNotification` for that and saves unless a text view still has keyboard input, as when another stage hands it over. `endEditing` gives keyboard input back to the stage's front window only while the panel still has it, so a click on another application keeps that application in front. Notes are dragged to reorder them, as groups are; a dropped note goes before the note under it, or last over the empty sidebar.

A note can lead to tabs. Dragging a tab while the sidebar shows the notes leaves the notes up instead of switching to the groups; dropping it on a note adds it to the note's tabs (a window already there is ignored), and dropping it on New Note starts a note linked to it, which may stay blank. Each link (`NoteLink`) keeps the window, its group then, and its name and application then; notes saved with the single `link` key of the first version load as one link. Each tab shows as a row on the note: a click switches to that tab wherever it is now, on whichever stage owns its group, and the button under the pointer takes it off the note. A click elsewhere on a linked note goes to its first tab, and a click on a tab a stage already shows in front does nothing, and a double-click, its pencil button or its context menu edits it; a single click on a linked note waits out the double-click interval before going to the tab, since going there first would take keyboard input from the stage and end the edit at once. Rows show the tab's current name (`StageModel.mapLinkedWindowNames`, refreshed only for linked windows so other title changes cost nothing); once the window is no longer managed, the row shows the saved name struck through and a click goes to the saved group if it still exists. Window ids do not survive the window, so a tab closed and reopened needs linking again.

The world clock's digits are drawn as segment displays (`SevenSegmentDisplay`): seven segments for digits, fourteen for letters. A display redraws only when its text changes; colons blink in a Core Animation layer so a blink costs the app nothing. The window server draws only while a layer's opacity changes, so the colons' fades are kept to 80 ms. Cities come from the time zone database and Apple Maps (`WorldClockCitySearch`); zones by offset, abbreviation or name from `TimeZoneSearch`.
