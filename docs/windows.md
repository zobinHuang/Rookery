# Windows and the stage

How MuxShots sees windows, takes them over, and lays them out on its stages.

## Seeing windows

- **Identity**: a window is its `CGWindowID` (`WindowId`). Accessibility elements carry no stable id, so the read-only private `_AXUIElementGetWindow` maps an element to its window id (`PrivateAccessibilityApi.swift`).
- **Window server**: `CGWindowListCopyWindowInfo` sees every window on every Space but gives no handle to move it. The private read-only `CGSWindowIsOrderedIn` tells windows really shown from those an app closed but keeps alive (Electron does).
- **Accessibility**: `kAXWindowsAttribute` lists only the current Space's windows. Windows on other Spaces are found by brute force through `_AXUIElementCreateWithRemoteToken`, in slices of ids up to a limit; only elements that are windows count, and an element once found stays valid across Spaces.
- **Tracking** (`WindowTracker`, `ApplicationWindowTracker`): an `AXObserver` per application on a run loop thread of its own, observing managed windows only. Window-level events are coalesced for 250 ms and read only the changed window; app-level structure changes and a 10-second fallback reconciliation read a full snapshot. Accessibility calls are synchronous IPC and can hang on a stuck app, so the main thread never makes them. A managed window that closed before it was ever observed is reported removed.

Nothing writes window-server state through private APIs; Spaces are never moved or switched.

## Taking windows over

- A window is managed only when the user drops it on a stage (or `muxctl manage`); other apps' windows are never touched. Dropping it on the content area alone does nothing, so a window merely dragged across the stage is left alone: while a window is over the content area, a pill (`ContentDropPill`) drops down at the top of it, and only a drop on the pill adds the window to the active group, or starts a group if there is none. The pill is a floating panel of its own, since the stage's front window covers the content area, and it lights up with the accent color while the window is over it. Likewise only New Group starts a group: the sidebar's empty space takes no window or tab, and a drop on a group adds to it as before.
- A dropped window is adopted only once it outlives the drop by 0.15 s: dragging a tab out of Chrome makes a window that Chrome merges back and closes at once.
- **Hiding** a window minimizes it to the Dock, and showing it gives it its frame while it is still minimized, so it opens straight into place, then restores it. So every managed window but the ones a stage shows sits in the Dock. Minimizing and restoring animate for about half a second, and macOS offers no way to turn that off; a minimized window takes a new frame and opens there, which keeps the switch to one move. Its `restoreFrame` and `homeFrame` are kept in `workspace.json`. A window the user minimized is told apart from one MuxShots hid by the workspace's hidden mark: it is never picked as a group's front window and stays in the Dock when windows are put back.
- **Why not park off screen.** Windows were once hidden by moving them past a corner of the display. macOS does not let a window leave the screen entirely, and a window with a sliver on screen counts as visible however little shows, so its application went on rendering it at full rate (an opaque window over the sliver did not change that): three parked VS Code windows whose terminals animated kept the GPU a fifth busy. A minimized window counts as unseen, and its application stops drawing it. An application could also be hidden whole, but only when every one of its windows was parked, which left VS Code, with one window on the stage, drawing the rest.
- **Hiding applications.** Half a second after layout settles, an application with hidden windows whose other windows shown on some Space nobody sees is hidden whole (`NSRunningApplication.hide`): windows off every display, such as the link bubble Chrome leaves, and windows wholly beneath a stage, such as a WeChat chat left under it, which kept WeChat drawing. One whose windows are all minimized draws nothing and is left as it is, so showing one of them does not wait for it to unhide. A hidden application is unhidden before any of its windows is shown again, and its windows are moved only once it is shown: unhiding finishes later and puts the application's windows back in its own order, and a hidden application's windows cannot be moved. A hidden application goes on working unseen, but it is not put in the background band (`setpriority` with `PRIO_DARWIN_BG`) any more: helpers started while their application was there inherited the band and starved under load, and twice that left the whole machine lagging, typing and the pointer included, with a load average above 700. `ApplicationThrottle` remains only to put back to normal, at launch and on every check, any application an earlier build left there. An application with another window on screen, or the active one, is left as it is. The window list of every window is not in front-to-back order, so what lies beneath a stage is read from the on-screen list. A browser playing a video in the sidebar is left alone too: a hidden browser stops drawing the page, and the video freezes. Each extension connection carries its browser's process id, the parent of the native messaging host, and a browser that starts playing one while hidden is unhidden. A hidden application's windows still exist in the window server's list, so the tracker does not take them for closed. An application can show itself again with no layout change, unhidden or activated by something other than MuxShots and then left, or close the last other window that kept it shown, so the same check also runs half a second after any application is unhidden or leaves the front, and every 30 seconds; one found showing itself again is logged at notice level, which the log keeps.
- **Windows their application orders out**: WeChat orders its window out a second or two after it is hidden, and Accessibility stops listing it. Showing such a window asks its application to reopen, as a click on its Dock icon does, and moves the window once it is listed again; a window that still cannot be moved stays marked hidden, so the next switch tries again. Putting every window back at launch and quit reopens them the same way, and a saved window that is ordered out still counts as alive: `CGWindowListCopyWindowInfo` with `.optionIncludingWindow` omits such a window, so liveness is read from the full list.
- **Crash safety**: on launch and on quit, every hidden or staged window is put back where it was and restored from the Dock, so no window is ever left minimized by MuxShots; a window an older build parked off screen is moved back the same way.

## Stages

- A stage (`StageController`) is a borderless, non-activating, resizable panel at normal level. It is kept just beneath its front window (`order(.below, relativeTo:)`), so the managed window looks hosted inside it while staying a real window of its app. AppKit orders a pressed window to the front, so a press on the stage puts it straight back beneath that window (`StagePanel.sendEvent`) rather than covering it until the window is brought forward.
- **Windows stay with their stage**: a managed window on a stage that something other than MuxShots moves or resizes, the user dragging its edge or its application moving it, is put back once the mouse is up and no stage is following a window: the front window into the content area, a hidden one restored from the Dock by something else minimized again. Dragging a front window by its title bar still carries its stage along, and a drop on another group or stage still moves it there; only releasing a window frees it. A window that cannot take the content area is left where it landed rather than moved again and again; one in native full screen is left alone.
- **Several stages**: each owns its own groups. A stage moves with its front window while that is dragged (coalesced relayout), and dragging the stage moves its windows.
- **Displays**: `StagePanel` overrides `constrainFrameRect` so AppKit does not pin it to one display, and settles on the display under the cursor after a move.
- **Display changes**: a display that comes, goes or wakes (a lid closed and opened, a monitor plugged in) makes macOS move windows by itself, and can move the origin of the window server's coordinates. One and four seconds after such a change, each stage is fitted back onto the display it is mostly on and its front window refitted, and every hidden window found out of the Dock is minimized again.
- Frames for layout come from Accessibility, not the window server: during Space animations the window server reports skewed frames.
- **Switching**: ⌃⌥1–9 and the group switcher (⌥⇥) switch groups; ⌘⇥ is taken over by an event tap (`KeyInterceptor`) only while a stage is in front, offering windows most recently used first across groups. The switcher wraps its cards into rows that fit the stage it opens over; while it is open the same tap takes the arrow keys, left and right wrapping across every card, up and down keeping the column. Each ⌘⇥ left to the system is logged with the reason (category `shortcuts`).
- **Focus that follows a hidden window**: a hidden window that takes focus in the application in front and keeps it for 150 ms is taken as chosen, and its group and tab are switched to, as when a notification or the Dock brings it forward. An application behind the one in front moving its own focus is not followed: that made clicks land on another tab. Right after a switch, though, focus on a hidden window is the switch's leftover, not a choice: the application switched away from can finish activating after the one switched to, since activation is asynchronous, and the one switched to can settle its focus on one of its own hidden windows (Chrome does). For 1.5 s such a focus is taken back to the window brought forward, whichever application it is in, and 300 ms after each switch MuxShots checks that the application in front is not focusing a hidden window, as focus changes during a switch are not followed. A click on the stage brings its front window forward 50 ms after the mouse is up unless the click asked for a switch, checked again when its turn in the layout queue comes, so it never activates the application being switched away from.
- **Show before hiding**: a stage switch moves the new front window into the content area and raises it before it minimizes the old one, so the content area is never left empty for the frames in between, which flashed.

## Sidebar

The sidebar is SwiftUI in the stage's hosting view: a header with the title the user sets under General in the settings (the Mac's local host name while it is empty), the Groups/Mixer/Notes switch, then the groups, the mixer or the quick notes, then sidebar videos, code agent limits, the world clock, and the toolbar. Colors are tokens in `StageColors` that follow the light and dark themes (dark is near black); theme changes crossfade through a snapshot of each stage.

Every assignment to an `@Observable` property redraws the views reading it, equal value or not, so `StageController.refresh` assigns only what changed, and a layout change tells the views once when it ends rather than once for each window it moves. Window names live in `StageModel.mapWindowNames`, read only by the texts showing them (`WindowNameText`, `GroupSubtitleText`): pages such as Gmail retitle their window every few seconds, and that must not rebuild the stage.

Drop feedback (a group outlined, an insertion mark) is cleared once the mouse is released, wherever the drag ends. SwiftUI does not always report a drag leaving a target: it can miss the exit when the row under it is rebuilt, and can report an entry after the mouse is up. So every entry, from a drag that began on this stage, another stage or another application, starts a watch for the release, and an entry that arrives after it clears at once; otherwise a group stayed outlined beside the selected one.

Tabs that do not fit scroll sideways, faded at an edge with more beyond it, and the bar scrolls to a tab when it is selected. The bar keeps only whether tabs lie past either edge, not the scroll offset, so scrolling does not rebuild the stage; the tabs' backgrounds are keyed by position, since a second view with a window's id would be where scrolling to that window lands.

**No SwiftUI animation runs for long on the stage.** While any SwiftUI animation runs, every frame redraws the whole stage on the CPU, its text and icons included: the tab bar's sliding selection cost a third of a second per switch and the refresh symbol a full core while it turned. Motion that lasts is Core Animation on a layer of its own instead, which the render server runs while the stage draws nothing: the selected tab's background (`TabHighlight`), the refresh symbol (`SpinningSymbol`), the clock's colons.

The settings (`SettingsView`) show in the content area: the gear in the sidebar header, or Settings in the menus while a stage is open, sets the front window aside as a switch would and shows them there, as cards of rows named for what they set, with no explanations under them, spread over up to three columns that fill the content area's width. The stage panel takes keyboard input meanwhile, for the city search and shortcut recording, and a click on the stage does not bring the window back. Closing them (the close button or escape) switches to the active group again, which brings its front window back; choosing a group or tab instead leaves the settings for that, and a switch from elsewhere that brings the window back takes them away. With no stage open they show in a window of their own.

The screen saver (`ScreenSaverView`) is another page of the content area, opened from the sidebar's toolbar: it sets the front window aside the same way and shows the text set under Screen Saver in the settings, large and centred, shrinking to fit when it is long. A click on it, or any key while the stage has the keyboard, closes it and brings the window back, through a local key monitor that exists only while it shows; closing the stage drops it. Nothing on it animates, so it costs nothing to draw while it stays up.

Quick notes (`QuickNotes`, `NotesView`) are shared by every stage and saved to `notes.json` beside the workspace whenever one changes. A click edits a note in place: the stage panel takes keyboard input as it does for renaming, the editor is a `TextEditor` that grows with the text, return adds a line, escape puts the text back, and a note left blank is deleted. A click anywhere else saves: on the sidebar's empty space (which also finishes a name being edited), on another note or mode, or outside the stage, which takes keyboard input from the panel; the editor watches `NSWindow.didResignKeyNotification` for that and saves unless a text view still has keyboard input, as when another stage hands it over. `endEditing` gives keyboard input back to the stage's front window only while the panel still has it, so a click on another application keeps that application in front. Notes are dragged to reorder them, as groups are; a dropped note goes before the note under it, or last over the empty sidebar.

A note can lead to tabs. Dragging a tab while the sidebar shows the notes leaves the notes up instead of switching to the groups; dropping it on a note adds it to the note's tabs (a window already there is ignored), and dropping it on New Note starts a note linked to it, which may stay blank. Each link (`NoteLink`) keeps the window, its group then, and its name and application then; notes saved with the single `link` key of the first version load as one link. Each tab shows as a row on the note: a click switches to that tab wherever it is now, on whichever stage owns its group, and the button under the pointer takes it off the note. A click elsewhere on a linked note goes to its first tab, and a click on a tab a stage already shows in front does nothing, and a double-click, its pencil button or its context menu edits it; a single click on a linked note waits out the double-click interval before going to the tab, since going there first would take keyboard input from the stage and end the edit at once. Rows show the tab's current name (`StageModel.mapLinkedWindowNames`, refreshed only for linked windows so other title changes cost nothing); once the window is no longer managed, the row shows the saved name struck through and a click goes to the saved group if it still exists. Window ids do not survive the window, so a tab closed and reopened needs linking again.

The world clock's digits are drawn as segment displays (`SevenSegmentDisplay`): seven segments for digits, fourteen for letters. A display redraws only when its text changes; colons blink in a Core Animation layer so a blink costs the app nothing. The window server draws only while a layer's opacity changes, so the colons' fades are kept to 80 ms. Cities come from the time zone database and Apple Maps (`WorldClockCitySearch`); zones by offset, abbreviation or name from `TimeZoneSearch`.
