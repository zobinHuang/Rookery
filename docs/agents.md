# Agents

The sidebar's Agents mode shows every code agent roost knows of, one crow each playing the state its session is in, and the content area shows one agent's conversation with a box to prompt it. What an agent is, and the events that move it between states, are in [resources](resources.md); how a prompt reaches its pane is in [rook's live link](../rook/docs/link.md).

## Following roost

`FleetModel` (one for the app) holds the fleet. With an address in Settings and the token in a file only the user may read (`FileSecret`, `roost-token` in the data directory, moved once from the keychain, where an unanswered prompt after a rebuild had left the app unconnected; a failed read is tried again on the next connect), it reads the agents and rooks over HTTP, then opens roost's live link as a desktop and applies each event to `AgentFleet` (`RookeryCore`): a state or an end changes the agent in place, a new agent is fetched. When the link drops it shows the last fleet with a banner and retries, backing off from 2 to 60 seconds, then reads everything afresh, so nothing between the drop and the reconnect is missed.

`RoostClient` (`RookeryPlatform`) is the only code that speaks roost's API.

## The sidebar

- Sessions only; a session's subagents fold under it behind a count.
- The user's teams first, then the rest by last activity, then those that ended, folded away.
- Teams live on roost ([teams](../rook/docs/teams.md)), so their agents know them too; an agent may be in several, and shows under each, tagged with the others. This Mac keeps only the layout in `agent-teams.json`: the order of the teams and of the agents in each, and which are folded. Teams made here before roost held them are carried over to it once. Drag an agent onto a team to add it, holding Option to move it out of the team it was dragged from; onto an agent in a team to put it before; onto New Team to start one; or onto Unassigned to take it out of the team it came from. Drag a team's header to reorder teams. A change shows at once and is written to roost; if roost refuses it, the sidebar says why and takes roost's teams back.
- Each agent's row shows what it works on now, or its role, as Rookery keeps them or the agent set them with `rook me`.
- A machine whose rook is offline dims its agents.

## The crows

`CrowRig` in `RookeryCore` draws the crow in flat facets lit from the top left, each state a crow's behaviour rather than a mark over its head: asleep on its perch with its head tucked (idle), gliding (thinking), beating its wings (working), pressing down a stack (compacting), calling out with its beak open and wings raised (needs approval), staring with its head cocked (needs input), spreading its wings (done), ruffled and off balance (error), hunched in the rain (rate limited), and an empty perch with a feather (ended); Raven is larger, with a raven's throat and wedge tail, guarding a letter or carrying one. The state's color shows only as a thin signal line under the perch. The crow is graphite in light themes and silver in dark ones, pure black or white in high contrast. Every act is a loop of continuous curves whose periods divide its length, so it ends where it begins (`CrowRigTests` checks each), centred on the box its whole loop fills, every agent's crow at one scale so it does not jump when its state changes.

`CrowView` and `RavenView` play them through `CrowAnimationView`: `CrowFrames` draws a loop off the main thread at the view's size in pixels and in the theme's colors, 30 frames a second or 60 for fast wingbeats, once however many crows show it, keeping the 32 most recently used; the view shows the still frame at once, then hands the frames to a discrete keyframe animation on its layer's contents, so the loops cost the app nothing while they play. Under Reduce Motion the still frame stays; while the window is hidden the loop holds.

## The agent's page

`AgentDetailView` reads the session's transcript from roost every two seconds, only the bytes it has not seen, through `TranscriptReader` (`RookeryCore`), which understands Claude Code transcripts and codex rollouts and keeps what a person reads: the prompts, the answers and one line per tool call. Prompts typed in its box go to `POST /v1/messages`; under the box, the latest prompts show what became of them (waiting while the agent is busy, delivered, or failed and why).

## Checking it without a person

Seed a roost of your own with agents (`POST /v1/events` with `started` and `state` events, a transcript through the session upload API) and render `StageView` offscreen with a `FleetModel` given an in-memory `SecretStore`, so the render never touches the token file; see docs/development.md for the harness.

## Rookmaster

The console over everything roost manages, opened from the top of the Agents sidebar. `FleetModel` keeps a `ResourceGraph` (`RookeryCore`) beside the fleet: every kind roost lists, all their resources, the relations between them and the latest hundred events, read in full on connecting and kept current by the same live link.

- **Board** (`RookmasterBoard`): a column per kind but memories (`RookmasterView.setConsoleHiddenKinds`), agents leftmost, each ordered by last use so what moved last rises, with an animation. Edges are the relations, but for an agent mounting or using a skill of a playbook it follows, which its line to the playbook and the playbook's to the skill already show; they are drawn from the cards' frames (anchor preferences), thicker for relations that happened more often, coloured by verb; a subagent's edges are drawn from its session's card. Two cards share one line whichever way things went between them, its width growing with how often, with an arrowhead at each end when they went both ways. A team's card folds its agents away and back (`PageMemory.setBoardFoldedTeams`, laid out by default): a folded team's agents leave the agents column, unless another team of theirs is laid out, and their lines, and their subagents', are drawn from the team's card, merged by where they go. Hovering or clicking a card brings forward it, its neighbours and the edges between them, and clicking where no card is lets it go; double-clicking opens it. Choosing a Raven conversation that is in a team, in the panel below the board, narrows the board to its teams, their agents and what those agents, their subagents and the playbooks they follow touch, with a chip naming the conversation at the head of the toolbar; clicking the chip, or the chosen conversation again, chooses none and shows everything. Lock freezes the order; the filters narrow by name, by time since last use, to live agents, and by kind.
- **A list per kind** (`RookmasterKindList`), with an editor beside it (`ResourceEditors.swift`):
  - skills are added by pasting their address (a GitHub or GitLab page of the skill's directory or its SKILL.md, or `owner/repo@path#ref`); the editor shows where the skill lives and the commit roost resolved, and changes its name, description and tracked ref, refreshes it, or removes it;
  - playbooks are created, edited and deleted: what they are for, their steps, and the skills they load. A step names a skill it uses with `@`; saving pins every skill the steps name (`PlaybookSteps` in `RookeryCore`), beside those added by hand;
  - memories have no list of their own: each shows on the page of the agent that wrote or changed it, or whose subagent did, as a tag under its role, focus and teams that opens the memory's editor (its name, project and text, saved or deleted) over the page;
  - agents are read-only, and any other kind is edited as a name and an attributes object.
  - no editor lists a resource's relations: the board draws them, and listing a busy agent's hundreds of them made opening it stall.
- **Log** (`RookmasterLog`): the latest hundred events, newest at the bottom, following as they are logged, with a filter; it folds to its title bar.

## Hosts and new agents

The Hosts tab of Rookmaster lists the concrete hosts of `~/.ssh/config` (patterns and `Match` blocks name none; `Include` is followed), each with the rook it runs: the one the user chose, else a rook named as the host or its short host name. A host's page checks over ssh what it has for agents (tmux, claude, codex, rook, and whether rook reports to a roost), installs rook where it has none (after asking: it runs rook's `setup.sh --name` and `rook connect` there, the token going over ssh's input, never a command line), and keeps the host's workdirs: a directory, browsable over ssh, with the harness, playbook, skills, role and teams an agent started there begins with. Hosts' settings and workdirs live in `hosts.json` in the app's data directory, since only this Mac's ssh configuration reaches the hosts. ssh runs with `BatchMode`, so a host that asks for a password fails rather than waiting.

New Agent, in the Agents list, on a host's page and on each workdir, starts an agent through roost rather than ssh: a spawn with a launch id ([the API](../server/API.md#messages)), which the host's rook-link starts in tmux after installing the playbook and skills; the session names its launch as it starts, and roost gives it its role and teams. Until it reports in, the launch shows as starting under the button; a rook that could not start it, or a session that never reports in within 90 seconds, shows why, naming the pane it was started in: a session in a folder Claude Code has not trusted waits there for a person to answer its trust prompt.

## Teams

The Teams tab of Rookmaster shows each team: its goal, which its agents are told; its members' cards with their role, focus, state and host, and their duty in the team, which the user edits in place; the messages roost holds for the user, each with its reason, Cancel and Let It Go, and nothing of what passed freely; a box to speak to the whole team as the user; and a switch, off by default, to have roost hold messages past the team's limits, which it then shows to change. The tab and the team's row count the messages still held. An agent's page shows its role, which the user may change, its focus and its teams.

Rookery keeps every rook agent's role (who it is to its teammates) and focus (what it works on now) written, so no one has to (`AgentIdentityKeeper`). Every 90 seconds it reads what each live agent's transcript grew by on roost, through a `TranscriptReader` begun where it last stopped, and digests it (`TranscriptDigest`: how many prompts and compactions, the first and latest prompts, the latest compaction summary and reply). An agent's identity is due once the user first prompts it and it lacks a role or a focus, and again after its context is compacted or 20 prompts later; Rookery then asks the code agent Raven runs on, with its smallest model, no tools and no session kept (`claude -p --model haiku --tools "" --no-session-persistence`, or `codex exec --ephemeral`), for one JSON line of each, and writes them with `role_source` and `focus_source` set to `auto` and `identity_checked_offset` set to the transcript's length. Where each came from decides what it may overwrite: a role the user wrote on the agent's page (`user`) or the agent wrote with `rook me role` (`agent`) is kept as written; one a launch gave (`launch`, which Raven always writes when it proposes an agent) is the starting point and is brought up to date like Rookery's own; a focus the agent set itself stands for an hour. Emptying the role on the agent's page hands it back to Rookery. A transcript first seen, or grown by more than 8 MB since, is read only at its last 2 MB, and its start for the first prompt; an agent the model failed for waits ten minutes.

## Raven

The Rookmaster console's panel under the board, which ⌘J folds away and opens again on Raven, asks Raven, Rookery's agent over the fleet, for something in plain words; `@` names a resource, completed from the graph (`Mentions` in `RookeryCore`), and the request carries each named resource's kind, name and id. `RavenAgent` runs Claude Code headless (`HeadlessAgent` in `RookeryPlatform`) in a workspace of its own under the data directory, laid out afresh for each request from the app's `Raven` resources (`Resources/Raven` in the repository):

Every conversation records where it was started (`RavenOrigin`: the board, Mail or the launcher). The panel lists the board's own; All lists every conversation, wherever started, each from Mail or the launcher marked so. A conversation started elsewhere does not open in the panel by itself.

- `CLAUDE.md`, its standing instructions, and `.claude/skills/`, Rookery's skills: `rookery-resources` (the command reference), `fleet-status`, `inspect-agent` and `triage-attention` (the agents' state, what one is doing, what waits on the user, through `rook-client agent status` and `agent tail`), `brief-agent` (a message, an interrupt or a new playbook for an agent, proposed), `start-agent` (a new agent on a host or workdir, with its playbook, skills, role and teams, proposed), `manage-teams` (a new team, a member and its duty, proposed), `direct-team` (directing a team the conversation is in), `team-report` (where a team stands and what blocks it), `register-skill`, `write-playbook`, `distill-playbook`, `tidy-memories`, `describe-skills` and `review-fleet`.
- `bin/rook-client`, the same client rook installs, and `config/rook/connect.json`, the app's roost address and token, readable by the user alone.
- `config/rook/hosts.json`, the user's ssh hosts with their rooks and workdirs, which `rook-client host list` reads: they live on this Mac, not on roost.

The box closes to one line once a request is sent, keeping the focus, and opens again with the next key; the conversation follows its end as the answer comes in unless the user scrolled up, Rookery's own scrolling never counting as theirs. A conversation is titled by its first request until Raven first answers; then Rookery writes a title of a few words from the request and the answer with the same small model (`QuickModel`), since `claude -p` writes none (`RavenConversation.titleSource`: none, `generated` or `user`, which a rename sets and no title written replaces), keeps it with the conversation and tells roost with a `renamed` event; the latest twenty conversations kept from before are titled when Raven first loads. The title heads the open conversation, the panel's list and the launcher's, and names the conversation in the log, as `Raven [title]`, since every one of them goes by the same name. A conversation runs on Claude Code or on Codex, chosen in the panel before it starts and kept for its turns (`RavenConversation.engine`). Codex runs as `codex exec --json` (`exec resume <thread>` for later turns) with none of the user's configuration, live web search, nothing asked of anyone, and `rookery-mail` as its MCP server, its commands sandboxed to the workspace with the network open for rook-client unless the turn may work on the Mac (below); it reads `AGENTS.md` and `.agents/skills`, copies of `CLAUDE.md` and the skills. Its events are translated into Claude Code's transcript form (`CodexTranslation`), so one reader shows both and proposals are found the same way. Its file changes and web searches become `Write`, `Edit` and `WebSearch` calls in that form.

Both get the user's mail and calendars from `rookery-mail` ([mail and calendars](mail.md)).

Claude Code runs with `--setting-sources project`, so neither the user's settings nor their hooks apply, and `--allowedTools "Bash(rook-client resource:*)" "Bash(rook-client agent:*)" "Bash(rook-client propose:*)" "Bash(rook-client host:*)" "Bash(rook-client team list:*)" "Bash(rook-client team roster:*)" "Bash(rook-client team send:*)" "Bash(rook-client message:*)" "Bash(rook-client inbox:*)" Skill WebFetch WebSearch Read Glob Grep TodoWrite Task`: it reads and changes roost's resources, reads the agents' state and transcripts, loads its skills, searches and reads the web and the Mac's files, and messages agents only as a member of a team (below), which roost enforces. Anything else it would do on the Mac, a command run or a file written, Claude Code asks of `rookery-mail`'s `approve_local_action`, passed as `--permission-prompt-tool`: the tool asks the running Rookery over its control socket (`ControlRequest.ravenApproval`, the conversation known from `ROOKERY_AGENT_ID`) and answers allow or deny once the user decides, however long that takes (`MCP_TOOL_TIMEOUT` is a day). Rookery shows the action as a card under the conversation (`RavenApprovalCard`: the command or the file, with what goes in it) with Allow Once, Allow in This Conversation and Decline; an action outside a turn under way, or when Rookery cannot be reached, is declined, and stopping a turn declines what it waits on. A command that reaches code agents around roost, one whose segments run `tmux`, `ps`, `pgrep`, `kill`, `lsof` or one of rook's own tools (`RavenApprovalRequest.reachesAgentsAroundRoost`), is turned down by the tool itself, without asking and whatever the conversation allows, with a reason pointing Raven at `rook-client agent status`, `agent tail`, `message` and proposals: an agent on this Mac is reached through roost as one on any other rook. Codex runs its commands without asking, so there the rule is its instructions alone. Allowing a conversation is kept with it (`RavenConversation.localAccess`), and the setting Raven on This Mac (under Roost) allows every conversation. Codex cannot ask action by action, so a turn on Codex that is neither allowed nor kept sandboxed asks first, as a whole (`RavenApprovalRequest.codexTurnTool`): Allow This Turn and Allow in This Conversation run it with `sandbox_mode="danger-full-access"`, Keep Sandboxed keeps the conversation to its sandbox from then on. Each conversation has a folder (`RavenConversation.folderPath`, by default `~/Documents/Raven`, created as a turn starts), chosen from the chip in its header, which also shows it in the Finder and changes what Raven may do; it goes to Claude Code with `--add-dir` and to both in their instructions (`RavenLocalWork.folderPrompt`), which say to write files with Write and Edit. The files Raven made for the user show in the conversation as files, once it presents them with `rookery-mail`'s `present_files` (its instructions say to pass only what the user should look at, not every file touched): each a card in place of the call (`TranscriptFileCard`: its icon, name and folder, Show in Finder and Open while it is on this Mac); the writes and edits along the way stay among the tool calls. A conversation opens at its last 256 KB of history (`RavenAgent.historyTailBytes`), so its latest messages show at once, the earlier ones read when the user asks at the top and its older proposals in the background, under a stand-in of bubbles that stays a moment after it is read while the conversation lays out beneath it. Raven can use the user's Chrome when Raven Uses Chrome is on (the default, under Roost): Claude Code runs with `--chrome`, Claude in Chrome's tools beside its own, those that only look (the tabs, a page's text or tree, finding on it, the console and the network, a screenshot or a scroll; `RavenApprovalRequest.setReadOnlyChromeTools` and `isReadOnly`) passing without asking and the rest (opening a page or a tab, clicking, typing, filling a form, running a script, uploading) asked as any action is, the card naming the step (`RavenApprovalRequest.verb`) and what is typed, clicked or opened; with the setting off it runs with `--no-chrome`. Codex, which reads none of the user's configuration, gets the Chrome plugin Codex bundles, enabled with `-c` overrides from `$CODEX_HOME/.tmp/bundled-marketplaces/openai-bundled`, once the user installed it from Codex's plugins (its cache under `$CODEX_HOME/plugins/cache/openai-bundled/chrome`) and only in a turn that may work on the Mac, as the plugin drives Chrome through Codex's node runtime and its own native host. Both are told what the browser is for and what never to do in it (`RavenLocalWork.browserPrompt`). A page Raven opens shows in the conversation as the page (`TranscriptPageCard`: its site and path, and Open), and Chrome and mail tools read as `Chrome navigate` or `Mail read thread` among the tool calls (`TranscriptView.shownName(ofTool:)`). In Raven's box, `@` offers files and folders too: in the conversation's folder by what is typed, or from `/` or `~`, a folder's path ending in `/` to go on into it (`Mentions.fileSuggestions`); the path goes into the request as typed. What it would do to an agent or on a rook it proposes with `rook-client propose`: `message`, `interrupt`, `approve` (allow the waiting call once, or decline it), `playbook` (load a playbook into a running agent's project in place of its own, then send it a message if one is given) or `spawn` (a new session in a directory on a rook); each checks its agent or rook and prints the proposal without doing anything, and also adds it to the file `ROOK_PROPOSALS_FILE` names, which Rookery sets for each conversation (`<id>.proposals.jsonl` beside its history), so a proposal shows even when Raven cut or filtered the command's output. `workdir` proposes a workdir for one of the user's hosts, a parent when `--parent` (each agent started in it gets `<path>/<MMDD-name>`, which its rook creates); a spawn for the rook a machine's host name names goes to that rook. Of the spawns waiting for one rook and directory only the latest shows, and starting one lets the others go. Starting a spawn that joins teams also puts the conversation that proposed it in those teams (`RavenAgent.joinTeams`), so the new session and Raven can message each other through roost. The app finds each proposal in Raven's output and history (`RavenProposal` in `RookeryCore`) and shows it under the conversation with a button that carries it out and Not Now; carrying it out posts it to roost as the user, as a delivery of its kind for the rook to perform (rook/docs/link.md), and follows the delivery. Each decision is kept with the conversation (`RavenDecision`) and told to Raven at the start of its next request.

To check the plumbing without calling a model, set `executableOverride` to a script that prints stream-json lines and runs `rook-client` itself, and `workspaceOverride` to a scratch directory.

### Raven in a team

What the user sends a conversation while it answers waits its turn (`RavenAgent.mapQueuedRequests`): each shows under the conversation as a faded, outlined bubble the user can take back on hover, and once the answer under way finishes, stopped or failed included, the oldest goes as the next request, one per turn, ahead of any teammates' messages waiting. A request sent while the queue holds any joins its end, so the order stays the user's. The queue lives in memory; quitting Rookery drops it.

The user puts a conversation in a team from its header (Join a Team, once it has begun), and takes it out from its chip or from the team's page, where it shows as Raven with a way to the conversation; the sidebar leaves it out of its teams. roost holds it to that team as any member (server/API.md#messages): it messages the team's members itself, with `rook-client message` and `rook-client team send`, named to rook-client by `ROOK_AGENT_ID` since it runs outside tmux, and reaches no one else. Its teammates read it as Raven, the user's assistant speaking for the user, in their rosters and in its messages (rook/docs/teams.md). Each request lists the conversation's teams and members. A conversation stays under way on roost between its turns, idle once a turn finishes, and ends only when the user removes it, so its teammates can always answer it; one roost holds as ended, as every conversation was once its turn finished before, is started again when it joins a team and when Raven first reads its messages after launch. Their answers wait on roost under the rook `rookery`; every four seconds while any conversation is in a team, `RavenAgent` reads them, reports each delivered, keeps each in its conversation in rook's own words (`RookMessage`), which the conversation shows as the sender's, not the user's, and wakes the conversation to answer them, or once it finishes the answer under way.

On the board, lines run from Raven's tab to what the conversation open in its panel works on, switching as another is opened (`RavenLinks`, placed by `RavenLinksOverlay` over the cards' anchors and swayed by Core Animation in `RavenLinksView`): to each team it directs, faint and slow for as long as it is in it, and to whatever it touched a moment ago, as roost's events tell (an agent it messaged, a skill, playbook, memory or team it changed) or as its inbox does (an agent that answered it), bright, swaying like a rope shaken from below with a light climbing it, fading out over nine seconds. SwiftUI only finds where each line runs, when the cards move; nothing is redrawn frame by frame.

A conversation streaming in stays cheap for the window around it. It is laid out in a hosting view of its own (`LayoutIsland`), as an agent's conversation on its page is, so a new line or a frame of scrolling lays out only the conversation: SwiftUI's host of the island would otherwise take AppKit's notice that the island's constraints need updating, sent on every frame the conversation scrolls, to mean its size may have changed and lay the whole window out again, so the island quiets that one method of its host class (`_layoutMetricsInvalidatedForHostedView`) while the notice still goes up the views; what streams in is shown at most five times a second (`RavenAgent.shownReader`), while the history and Raven's own logic take every line at once; it follows its end with one scroll for each burst, and only the user's own scrolling, never a scroll of Rookery's or the content growing, decides whether it still follows; an answer's lines appear without popping in, since an animation kept running by line after line would lay the conversation out on every frame; and the dots that wait on an answer run in Core Animation. The cost was measured with a stand-in for claude that streams ten lines a second: a core held at full before, about a third after; scrolling such a conversation took 26 ms a frame and takes 4.

### Git credentials

Settings, Roost, Git Credentials keeps a token for each git host the user's private skill repositories live on (`GitCredentialsSettings`), on roost rather than on this Mac (server/API.md#git-credentials): each host with its user name and the token's last four characters, to replace or remove, and a form to add one, with a repository to try it on, which roost reads with the token it keeps for its host. roost reads private repositories' refs with them, and a rook installing a skill asks roost for the token of its repository's host (rook/docs/playbooks.md), so no machine needs git set up by hand.
